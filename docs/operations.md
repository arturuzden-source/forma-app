# Эксплуатация: запуск, обновление, восстановление

## Схема

Один сервис Railway: API, собранный интерфейс Mini App, Telegram-бот (long polling) и планировщик. Одна реплика. База SQLite и пользовательские файлы лежат на Railway Volume, подключённом в `/data`.

```
/data/forma.db          база (WAL)
/data/files/            фотографии и другие файлы пользователя
/data/backups/ГГГГ-ММ-ДД/  ежедневные копии (база + файлы + manifest.json)
```

## Переменные окружения

Все значения задаются в Railway → сервис → Variables. Пример без значений — в `.env.example`.

| Переменная | Кто задаёт | Назначение |
| --- | --- | --- |
| `TELEGRAM_BOT_TOKEN` | владелец | токен бота от @BotFather (секрет) |
| `OPENAI_API_KEY` | владелец | ключ OpenAI (секрет) |
| `OWNER_TELEGRAM_ID` | владелец | единственный аккаунт с доступом |
| `PUBLIC_URL` | настроено | адрес сервиса для кнопки Mini App |
| `DATA_DIR` | настроено | `/data` — путь Volume |

Без токена бота и `OWNER_TELEGRAM_ID` сервер запускается, но API отвечает 503, а бот выключен.

## Запуск и остановка

- Сборка: `npm run build`. Запуск: `npm start`. Проверка состояния: `GET /healthz`.
- Обновление: push в ветку `main` → Railway собирает и разворачивает новую версию. Пока проверка `/healthz` не прошла, трафик остаётся на старой версии; сервис с Volume останавливает старое развёртывание перед стартом нового, поэтому бывает короткая пауза в несколько секунд.
- Остановка: Railway отправляет SIGTERM. Сервер останавливает бота, дожидается текущих задач, закрывает HTTP, записывает WAL в базу и выходит. Через 20 секунд выход принудительный.
- Перезапуск: Railway → Deployments → Restart, или команда redeploy.

## Служебные функции

Наружу не публикуются. Служебный сервер слушает `127.0.0.1:3001` внутри контейнера:

```
railway ssh
curl -s http://127.0.0.1:3001/status
curl -s -X POST http://127.0.0.1:3001/backup
```

В боте владельцу доступны `/status` и `/aieval` (проверка моделей с подтверждением расходов).

## Резервные копии

- Ежедневно в 01:10 UTC: онлайн-бэкап SQLite штатным механизмом (`db.backup`), копия файлов, проверка `integrity_check`. Результат записывается в таблицу `backups`.
- Хранение 30 дней (`BACKUP_RETENTION_DAYS`), старые копии удаляются автоматически.
- **Ограничение:** копии лежат на том же Volume. Независимая копия за пределами Volume ещё не настроена — место хранения выбирает владелец.

## Восстановление

1. Выбрать копию: `/status` в боте или `ls /data/backups` через `railway ssh`.
2. Задать переменную `RESTORE_FROM=ГГГГ-ММ-ДД` — сервис перезапустится.
3. При старте, до открытия базы, текущая база и файлы переносятся в `/data/before-restore-<время>/`, копия проверяется и восстанавливается. Повторно с тем же значением восстановление не выполняется.
4. Проверить данные в приложении и удалить переменную `RESTORE_FROM`.
5. (С появлением удаления данных) после восстановления повторно применяется журнал удалений до открытия доступа.

## Миграции базы

- Миграции в `server/db/migrations.ts`, применяются при старте по порядку, каждая в своей транзакции. Применённую миграцию не меняем: изменение — новая запись в конце.
- Только совместимые вперёд изменения: добавить таблицу или столбец можно, удалять и переименовывать — в два шага через несколько версий.
- Перед миграцией, меняющей данные, создаётся ручная копия: `POST /backup` на служебном порту.

## Неудачное обновление

1. Если новая версия не прошла `/healthz`, Railway её не включает — работает старая.
2. Если версия упала после запуска: Railway → Deployments → предыдущее успешное развёртывание → Rollback. Данные на Volume остаются.
3. Если новая версия успела применить миграцию, старый код продолжит работать, так как миграции только добавляют. При повреждении данных — восстановление из копии (см. выше).
